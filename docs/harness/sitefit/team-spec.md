# 사이트핏 Harness 팀 스펙

## 목적
사이트핏 작업이 제품 의도에서 구현과 검증까지 일관된 산출물로 이어지도록 재사용 가능한 작업 파이프라인을 정의합니다.

## 현재 저장소 맥락
- 이 저장소는 사이트핏 앱 코드와 휴대용 Codex 설정, Harness 관련 스킬을 함께 보관합니다.
- 현재 앱은 Node.js 내장 모듈 기반 서버, 정적 프론트엔드, JSON 파일 저장소로 구성되어 있습니다.
- 외부 AI 연동은 아직 실제 API가 아니라 `mock` chat client 경계를 사용합니다.

## 아키텍처 패턴
기본은 순차 파이프라인입니다. 요구사항, 디자인, 구현, QA는 앞 단계 산출물에 의존합니다. 전문 시스템은 필요한 경우에만 선택적으로 사용합니다.

## 역할 구조
- Harness: 작업 분류, 워크플로 선택, 통합, 충돌 해결, 최종 검증을 담당합니다.
- Superpowers: PRD, 스펙, 구현 계획, 수용 기준, 테스트 전략, 리스크 정리에 사용합니다.
- Open Design: UX/UI 흐름, 프로토타입, 컴포넌트 스펙, 접근성, 디자인 QA에 사용합니다.
- gstack: 코드 구현, 리팩터링, 기술 리뷰, QA, 문서 갱신, 릴리스 준비에 사용합니다.

## 요청 유형
- 작은 작업: 직접 실행 후 최종 검증.
- 기획 중심 작업: 접수, 스펙, 수용 기준 작성 후 승인 또는 구현.
- 디자인 중심 작업: 접수, 필요 시 스펙, 디자인 핸드오프, 구현.
- 개발 중심 작업: 접수, 필요 시 구현 계획, 코드, 리뷰, QA.
- 전체 제품 기능: 접수, 스펙, 디자인, 구현, 리뷰, QA, 최종 검증.

## 핸드오프 파일
- `_workspace/01_intake.md`: 목표, 맥락, 가정, 범위, 리스크, 수용 기준.
- `_workspace/02_spec.md`: 제품 및 기술 요구사항.
- `_workspace/03_design_handoff.md`: UX 흐름, 컴포넌트 동작, 상태, 접근성 메모.
- `_workspace/04_implementation_notes.md`: 변경 파일, 결정 사항, 트레이드오프, 마이그레이션 메모.
- `_workspace/05_review.md`: 리뷰 발견 사항, 심각도, 해결 상태.
- `_workspace/06_qa.md`: 검증 명령, 수동 점검, 실패 내역, 잔여 리스크.
- `_workspace/07_final_verification.md`: 원래 목표 대비 최종 수용 검증.

## 충돌 처리 기준
1. 사용자 목표.
2. Harness 통합 결정.
3. Superpowers 요구사항과 수용 기준.
4. Open Design 핸드오프.
5. gstack 구현 세부사항.

요구사항은 기술적으로 불가능하지 않은 한 디자인과 구현보다 우선합니다. 디자인 핸드오프는 시각적 가정보다 우선합니다. 기술적 차단 요소는 Harness에서 최종 판단합니다.

## 실패 처리 기준
- 목표가 불명확하면 `_workspace/01_intake.md`에 가정을 기록하고, 방향을 크게 바꾸는 결정만 질문합니다.
- 빌드/테스트 명령이 없으면 검증 통과처럼 쓰지 않고 한계를 기록합니다.
- 구현 중 누락된 제품 요구사항이 발견되면 접수/스펙 문서를 갱신합니다.
- 디자인과 구현이 충돌하면 양쪽 메모를 보존하고 Harness가 경로를 선택합니다.

## 검증 체크리스트
- 요청 유형이 기록되어 있어야 합니다.
- 실질 구현 전에 수용 기준이 있어야 합니다.
- 선택한 워크플로에 필요한 핸드오프 파일이 존재해야 합니다.
- 실행한 명령과 실행하지 못한 명령을 포함해 검증 근거가 기록되어야 합니다.
- 최종 응답은 결과를 원래 사용자 목표에 다시 연결해야 합니다.
